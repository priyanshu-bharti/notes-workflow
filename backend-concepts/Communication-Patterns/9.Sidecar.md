## Sidecar Pattern

- Every protocol needs a library for interfacing.
- For instance HTTP library (in any language) is required to make/handle HTTP requests.
- This is the case on both sides (client and the backend) which needs to use the same library.
- In a large distributed application, changing the underlying library is hard.
- Changing the library requires:
  - Retesting
  - Ensuring Backwards Compatibility
- Thus adding features becomes hard and microservices suffer.

### Sidecar Pattern

- In this pattern, the client and the server backends both let a connected proxy communicate between themselves.
- Proxy has a rich library while the client has a thin library.
- Sidecars are support containers which shares the lifecycle and environment with the primary services but is independent in terms of logic and deployment.
- The client in this case isn't typically the frontend, it is the primary backend service relying on other backend to perform some task.
- Let’s say you have a backend API service that does business logic and needs to:
  - Log request traces.
  - Handle retries and rate-limiting.
  - Encrypt/decrypt sensitive data.
- You could:
  - Keep the core app focused only on business logic.
  - Run a sidecar proxy (like Envoy or custom sidecar) to:
    - Handle rate-limiting.
    - Forward logs.
    - Handle secure TLS termination or encryption.
- Here Your main service is the client of the sidecar.
- The sidecar is a backend process helping the main backend.

### Pros and Cons

| Pros                                                                   | Cons                                                                                  |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Separation of concerns: Keeps app logic clean.                         | Operational overhead: More moving parts and complexity in deployment.                 |
| Reusability: Same sidecar can be reused across multiple services.      | Resource usage: Each sidecar consumes CPU/memory alongside the app.                   |
| Polyglot friendly: Sidecars can be written in any language.            | Debugging complexity: Issues may span both containers.                                |
| Scalability: Easier to manage shared concerns like metrics or logging. | Tight coupling: Lifecycle is shared — failure in the sidecar may impact the main app. |
| Standardization: Centralized behavior like rate limiting or retries.   |                                                                                       |
