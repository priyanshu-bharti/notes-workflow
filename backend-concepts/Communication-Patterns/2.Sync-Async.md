## Sync vs Async Workloads

- Synchronization simply means that the caller and the responder both work for the same thing at the same time.
  - Think of this like a button which onClick, executes some RPC on the responder.
  - Meanwhile the caller is blocked from executing other tasks.
  - The responder starts executing the function.
  - Then the caller can move to the next task once the responder has returned with some result.
  - So in an essence both caller and responder are doing the same thing while one waits for the other.
- Now, if you wanted to do something else while the responder was busy doing its thing, you could not do it in the traditional synchronous style.
  - Say you wanted to run timers, or update some data, or listen for some events, you could not do it.
- We didn't use the term client or server since async work happens everywhere.

### How Sync stuff works

Consider the following code:

```js
// Program Starts
// Program uses CPU to do something
doWork();

// Program reads from the disk
readFile("largeFile.dat");

// Program Resumes
// Program does more work
doMoreWork();
```

- JS engine does some work `doWork` which requires CPU.
- Then, the caller program sends the request to read the file and blocks.
- Now, the JS execution engine can't get past the `readFile` since JS is single threaded.
- So `doMoreWork` can't start early since the `readFile` has not returned.
- This is the reason why the caller and the responder are both in sync.

### How Async stuff works

- Consider the same code, but this time the `readFile()` call is an async function call.
- Now, the JS engine first executes `doWork()`.
- Then the `readFile()` is called and JS Engine spawns a new thread which reads the disk.
- This new thread blocks while our main thread moves onto executing `doMoreWork()`.

#### Under the hood

- The caller can work until it gets a response from the worker thread.
- The caller can use the following system calls (For reading from a disk):
  - `EPOLL`: Linux system call for IO events which caller will poll for file descriptors to be ready.
    - macOS uses `kqueue` and windows uses `IOCP`
  - `IO_URING`: Linux System call for storage device async IO operations. (The responder will notify the caller when the reading has been done.)
- If during async I/O, Node can't make the above system calls, then it just spawns a new thread and let it get blocked while Node itself remains unblocked.
- The caller and the responder is not in sync.

### Examples of Async Workloads

- Async Programming (Coroutines/Promises/Futures) like in Python/Go/Node.js/Java
- Async Processing using Queues (Put to the queue and get an ACK with JobId and wait for events.)
- Async Commits in Postgres Using Write-Ahead Logs and Pages.
- Async IO in \*NIX Systems.
- Async Replication in Postgres

#### Annexure: How Async Commit Works in Postgres.

- During a transaction, all the changes are written to an in memory view of a table (in blocks of 8KB).
- All the mutations are applied sequentially and Postgres maintains a log of all operations.
- In sync commits, after the mutations, the contents of the WAL will get flushed to the disk and the transaction will commit.
  - The actual data changes from the Pages are applied at some later point.
- But in async commits, the commits are done as soon as the entries are written in the WAL are marked for commit.
  - If the system crashes before the WAL is flushed to the disk, then those transactions are lost.
- On startup Postgres checks the savepoint and replays all the changes from the WAL to restore DB to last consistent state.

#### Annexure: How Replication Works in Postgres.

- Synchronous Replication
  - The Primary (Leader) generates WAL records. While the Standbys (followers) gets the WAL Records.
  - The Primary waits for all the standbys to replicate the logs and flush them onto the disk and then ACK is sent to the primary.
  - Only after getting ACK from all the standbys the transaction is considered committed.
- Async Replication
  - Primary generates the WAL records and sends them to the standbys.
  - Primary then marks the replication as committed without waiting for the ACK.
  - Standbys reads the logs and flushes the mutations onto the disk.
    - This may happen in real-time or the standbys may lag behind.
